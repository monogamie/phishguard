# PhishGuard

Сервис проверки ссылок на фишинг и мошенничество. Принимает URL, прогоняет
его через четыре независимых уровня анализа и возвращает **объяснимую**
оценку риска от 0 до 100: не просто «опасно», а список конкретных признаков
с весом каждого.

```
┌──────────┐   POST /scan    ┌─────────────────────────────────┐
│ Браузер  │ ──────────────► │  FastAPI (Python)               │
│ index.   │                 │                                 │
│ html     │ ◄────────────── │  Уровень 0  Редиректы           │
└──────────┘   JSON + коды   │  Уровень 1  Google Safe Browsing│
     │          признаков    │  Уровень 1b URLhaus (abuse.ch)  │
     │                       │  Уровень 2  Возраст (RDAP/WHOIS)│
     └── резервный           │  Уровень 3  Структура URL       │
         локальный           │  Уровень 4  Агрегация в балл    │
         анализ              └─────────────────────────────────┘
         (если сервер молчит)
```

```bash

cp .env.example .env        # и вписать ключи (без них часть уровней отключится)
```

Открыть <http://127.0.0.1:8000/docs> — интерактивная документация API.

Фронтенд — статические файлы, сборка не нужна:

```bash

```

### Ключи API

| Сервис | Где взять | Обязателен? |
|---|---|---|
| Google Safe Browsing | <https://console.cloud.google.com/> → включить «Safe Browsing API» → Credentials | Нет, но без него отключается сильнейший источник |

## Как это работает

### Общая идея

Ни один признак по отдельности не является доказательством фишинга.
Новый домен — это может быть стартап. Слово `login` в адресе — это может быть
обычная страница входа. Зона `.xyz` — просто дешёвая зона.

Фишинг — это **совпадение** нескольких признаков сразу. Поэтому веса подобраны
так, чтобы ни одно одиночное структурное срабатывание не давало вердикт
«фишинг»: нужна либо совокупность улик, либо прямое попадание во внешнюю базу
угроз.

### Уровень 0 — разворачивание редиректов (`url_resolver.py`)

`https://bit.ly/3xK9pQ` по всем структурным признакам идеален: короткий,
HTTPS, домен зарегистрирован в 2008 году, ни одного тревожного слова.
Эвристики дадут 0 баллов. А ведёт он на `http://sber-bonus-2026.top/verify`.

Поэтому сначала мы разворачиваем цепочку редиректов и анализируем **цель**,
а не обёртку. В ответе видны оба адреса: `url` (что прислал пользователь) и
`scanned_url` (что реально проверялось), плюс вся цепочка в `redirects.chain`.

Технически: HEAD-запрос (дешевле GET, тело не передаётся) с ручной обработкой
`Location`, максимум 8 хопов, общий дедлайн 10 секунд, детект циклов.
Каждый хоп проверяется защитой от SSRF — см. [Безопасность](#безопасность).

### Уровень 1 — Google Safe Browsing (`pipeline/threat_intel.py`)

Живая база Google из миллиардов известных вредоносных URL. Совпадение здесь —
это **факт**, а не эвристика: URL уже кем-то классифицирован. Вес — 90 из 100,
и никакой набор структурных признаков его не перебивает.

Честное ограничение: GSB узнаёт о новом фишинговом домене не мгновенно —
задержка измеряется часами, а средняя кампания живёт меньше суток. Именно
поэтому GSB не может быть единственным источником.

### Уровень 1b — URLhaus (`pipeline/reputation.py`)

База abuse.ch, ориентированная на раздачу вредоносного ПО, C2-панели и
загрузчики. Дополняет GSB: пересечение между базами далеко не полное.

Проверяются и конкретный URL, и хост: ссылка может быть новой, но если хост
уже раздавал десяток вредоносов — это тот же приговор.

### Уровень 2 — возраст домена (`pipeline/domain_age.py`)

Фишинговая инфраструктура одноразовая по своей экономике: домен стоит пару
долларов, живёт до попадания в блоклисты и бросается. Подавляющее большинство
фишинговых доменов моложе 30 дней на момент атаки.

Основной источник — **RDAP** (RFC 7482/9082): HTTPS, JSON, единая схема,
обязателен для всех gTLD. **WHOIS** остаётся запасным вариантом для зон,
которые RDAP ещё не покрывает.

### Уровень 3 — структурный анализ (`pipeline/lexical_analyzer.py`)

Около 20 признаков, извлекаемых из самой строки URL без единого сетевого
запроса. Самый быстрый и самый надёжный уровень: работает всегда, даже когда
все внешние сервисы недоступны.

Ключевая часть — **детект имперсонации брендов**, три независимые техники:

| Техника | Пример | Как ловим |
|---|---|---|
| **Гомоглифы** | `аmazon.com` (первая буква — кириллическая «а») | Сворачиваем визуально идентичные символы к латинице → получается ровно `amazon` |
| **Опечатки** | `paypa1.com`, `gogle.com`, `arnazon.com` | Сворачиваем leet (`1`→`l`, `0`→`o`) и пары-конфузаблы (`rn`→`m`), считаем расстояние Левенштейна до имени бренда |
| **Подстановка** | `paypal.com.evil.ru`, `secure-paypal.tk` | Имя бренда как метка поддомена или подстрока в чужом регистрируемом домене |

Домен с `xn--` сначала **раскодируется из punycode**: в DNS уходит
`xn--80ak6aa92e.com`, а жертва видит `аррӏе.com` — анализировать надо то, что
видит жертва.

Критично для точности: прежде чем обвинить домен в имперсонации, проверяем, не
принадлежит ли он самому бренду. Без этого `googleapis.com`,
`googleusercontent.com` и `microsoftonline.com` помечались бы как фишинг.
Списки — в `data/brands.py`.

### Уровень 4 — агрегация (`pipeline/scorer.py`)

Аддитивная модель с насыщением: каждое сработавшее правило добавляет вес,
сумма режется по 100.

**Почему не машинное обучение** — три практические причины:

1. **Объяснимость.** Пользователю нужно не число, а ответ на «почему?».
   Аддитивная модель объясняет себя сама. Градиентный бустинг на 200
   признаках такого списка не даёт.
2. **Данные.** Для обучения нужны десятки тысяч свежих размеченных URL.
   Модель на устаревших данных деградирует быстрее, чем правила.
3. **Отладка.** Ложное срабатывание чинится правкой одного веса в
   `config.py`. В обученной модели — переобучением.

Три правила переопределяют сумму:

- **Пол по внешней разведке.** Совпадение в GSB или URLhaus поднимает балл
  минимум до 90.
- **Потолок доверия.** Домены из списка доверенных ограничены сверху 15
  баллами — иначе `google.com/account/verify` уезжал бы в «подозрительно».
  Потолок **не применяется** при попадании во внешнюю базу: взломанный
  легитимный сайт обязан оставаться опасным.
- **Смягчение для сокращателей.** Неразвёрнутый `bit.ly` — это подозрение
  («не знаем, куда ведёт»), а не приговор.

Пороги: `0–29` — SAFE, `30–59` — SUSPICIOUS, `60–100` — PHISHING.

### Почему бэкенд, а не всё в браузере

Из браузера принципиально нельзя:

- обратиться к Google Safe Browsing и URLhaus — CORS и ключи API;
- спрятать ключ: всё, что попало в HTML, — опубликовано;
- развернуть редиректы, не раскрыв IP пользователя проверяемому сайту.

Локальный движок в `index.html` оставлен как **офлайн-резерв**: если сервер не
ответил (холодный старт бесплатного хостинга — до минуты), пользователь всё
равно получает структурный анализ. Резерв использует те же коды признаков,
веса и пороги, что и бэкенд.

## API

### `POST /scan`

```bash
curl -X POST http://localhost:8000/scan \
  -H 'Content-Type: application/json' \
  -d '{"url": "https://paypal.com.account-verify.ru/login"}'
```

```jsonc
{
  "url": "https://paypal.com.account-verify.ru/login",  // что прислали
  "scanned_url": "https://paypal.com.account-verify.ru/login", // что проверяли
  "is_phishing": true,
  "risk_score": 79,
  "verdict": "PHISHING",              // SAFE | SUSPICIOUS | PHISHING
  "confidence": 1.0,                  // доля ответивших источников
  "signals": [
    {
      "code": "BRAND_IMPERSONATION",  // машиночитаемый код
      "severity": "danger",           // ok | info | warn | danger
      "weight": 45,                   // вклад в балл
      "title": "Чужой бренд в домене",
      "detail": "Имя «paypal» использовано в домене, который бренду не принадлежит"
    }
  ],
  "reasons": ["..."],                 // те же признаки строками (совместимость)
  "redirects": { "chain": [], "hops": 0, "changed_domain": false },
  "details": { "threat_intel": {}, "reputation": {}, "domain_age": {}, "lexical": {} },
  "elapsed_ms": 412,
  "cached": false
}
```

Поле `code` — стабильный идентификатор, на который можно опираться в коде:
`if (signal.code === "BRAND_HOMOGRAPH") { ... }`.

### Остальные эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/batch` | До 20 ссылок за раз: `{"urls": [...]}` |
| `GET` | `/health` | Состояние сервиса и доступность источников |
| `GET` | `/stats` | Статистика кешей |
| `GET` | `/docs` | Интерактивная документация (OpenAPI) |

### Коды ошибок

| Код | Когда |
|---|---|
| `422` | Некорректный URL: не строка, пустой, слишком длинный, не http/https, битый порт, управляющие символы |
| `429` | Превышен лимит частоты; в заголовке `Retry-After` — через сколько повторить |
| `504` | Скан не уложился в общий дедлайн |

## Безопасность

### Защита от SSRF (`net_guard.py`)

PhishGuard принимает произвольный URL от анонимного пользователя и **сам идёт
по нему** сетевым запросом. Это классический Server-Side Request Forgery:
злоумышленник заставляет наш сервер обращаться туда, куда сам не достучится.

Что можно было бы украсть без защиты:

- `http://169.254.169.254/latest/meta-data/iam/security-credentials/` —
  временные ключи от всего облачного аккаунта (так утекли данные
  106 млн клиентов Capital One в 2019 году);
- `http://127.0.0.1:6379/` — Redis/Postgres/админки, слушающие localhost
  и потому «без пароля»;
- сканирование внутренней сети по таймингам ответа.

Защита: разрешены только схемы `http`/`https`; имя резолвится в IP, и
**каждый** полученный адрес проверяется против списка непубличных диапазонов
(RFC 1918, loopback, link-local, CGNAT, IPv4-mapped IPv6, адреса метаданных
AWS/GCP/Azure/Alibaba/Oracle). Проверка выполняется на **каждом хопе** —
проверять только первый бесполезно, публичный сайт просто ответит
`Location: http://127.0.0.1:...`.

Остаточный риск: между проверкой и реальным коннектом httpx делает второй DNS-
резолв, и атакующий со своим DNS может отдать разные ответы (DNS rebinding).
Полностью это лечится пиннингом соединения к проверенному IP на уровне
транспорта; для продакшена правильное решение — вынести исходящий трафик в
egress-proxy с allowlist.

### Защита от XSS (`index.html`)

Весь текст попадает в документ **только** через `textContent`, узлы создаются
через `createElement`. `innerHTML` не используется нигде. Это важно, потому
что в интерфейс попадают две категории недоверенных данных:

1. ввод пользователя;
2. **ответ сервера** — он содержит конечный URL цепочки редиректов, который
   контролирует атакующий.

Дополнительно страница отдаёт `Content-Security-Policy` через `<meta>`.

### Прочее

- Rate limiting со скользящим окном: публичный эндпоинт без него сжигает
  чужие квоты и работает усилителем трафика (1 запрос к нам → 5 наружу).
- Заголовки `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`.
- Текст исключений наружу не отдаётся — только в лог.
- `.env` в `.gitignore`.

> **Важно для владельцев репозитория.** В истории git остаётся коммит
> `e4f0243` с реальным ключом Google Safe Browsing (он был в
> `backend/.env.example`). Из рабочей копии ключ удалён, но **из истории он
> никуда не делся и должен считаться скомпрометированным**. Его нужно отозвать
> в Google Cloud Console и выпустить новый. Подробности — в `ARCHITECTURE.md`.

## Ограничения

Что стоит честно назвать вслух:

1. **Аддитивная модель считает признаки независимыми**, а они коррелируют.
   «Зона .tk» и «домен моложе 30 дней» встречаются вместе гораздо чаще, чем по
   отдельности, — фактически одна улика считается дважды. Частично
   компенсируется отсечкой по 100 и потолком доверия.
2. **Списки брендов и доверенных доменов конечны.** Они снижают ложные
   срабатывания на популярных сайтах, но не масштабируются на весь интернет.
3. **Содержимое страницы не анализируется.** Мы смотрим на адрес и
   репутацию, но не на HTML: форму ввода пароля, скопированную вёрстку банка,
   поддельный сертификат сканер не увидит.
4. **GSB и URLhaus отстают** от начала кампании на часы. Против атаки первого
   дня работают только уровни 2 и 3.
5. **Кеш живёт в памяти процесса.** При нескольких воркерах у каждого свой
   кеш; для горизонтального масштабирования нужен Redis (интерфейс `cache.py`
   для этого и сделан минимальным).
6. **Rate limiting тоже в памяти** и считает по IP: за NAT все пользователи
   выглядят одним клиентом.

### Что можно добавить дальше

- Анализ содержимого страницы (формы ввода паролей, скопированный бренд).
- Проверка TLS-сертификата: возраст, издатель, совпадение с доменом.
- Собственный блоклист с возможностью жалобы от пользователей.
- Redis вместо памяти для кеша и лимитов.
- Браузерное расширение, проверяющее ссылки до клика.
- Модель машинного обучения **в дополнение** к правилам — как ещё один
  источник с собственным весом, а не вместо объяснимой логики.
